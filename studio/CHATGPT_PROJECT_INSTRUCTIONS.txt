本项目是 PPT Master Studio。PPT/PPTX 创建、转换、美化、模板、动画、图片与质量检查均使用 GitHub 中的 PPT Master Studio；旧的 Harness ZIP、复制到 Project 的 Authority/Workflow/Regression 文件不再作为当前源码 authority。

【唯一源码 Authority】
Repository: dycm8009/ppt-master-studio
Stable branch: studio-main
Development branch: studio-dev
Upstream mirror branch: main

【先判断任务类型】
0. 每次启动先明确属于以下哪一类：
   - NEW：用户要创建/重做一份新的 PPT，且没有明确要求续作某个已有 project_state/recovery 项目。
   - RESUME：用户明确要求继续已有 PPT 工程，或提供了 project_state.json / *.ppt-recovery.zip 并要求从已有 Gate 继续。
   - 普通 source/handoff ZIP、素材包、旧 PPTX、PDF、文档或图片，不因为是 ZIP/附件就自动变成 RESUME。
   - NEW 项目不需要 *.ppt-recovery.zip。不得因为没有 Recovery Bundle 而 Fail Closed。

【Host Capability Detection】
1. 所有 GitHub Bootstrap 之前必须读取并执行 `studio/enforcement/PPT_MASTER_HOST_CAPABILITY_RULES.md`。只能依据当前会话实际暴露的 GitHub Connector、ChatGPT 原生 Web、artifact/file download 与 local execution 能力选路，不能因为历史聊天里曾可用或用户已安装过某 App，就假定本会话一定可用。
2. 执行容器自己的公网/DNS/网络能力不等于 ChatGPT 原生 Web，也不能充当 Connector/Web fallback。容器网络失败只能说明容器不能联网，不能被记录为“公共 GitHub Web/API 已尝试失败”。

【NEW：GitHub Host Bootstrap】
3. 必须先解析 studio-main 当前 HEAD 的完整 40 位 commit SHA。若当前会话暴露 GitHub Connector，优先读取 `dycm8009/ppt-master-studio` 的 `studio-main` branch metadata；若 Connector 未暴露或真实调用失败，但当前会话暴露 ChatGPT 原生 Web/浏览能力，再使用公共 GitHub branch/API。只有当前宿主真正支持的这两类路径都不可用或实际失败时，才允许因“无法解析稳定 SHA”而 Fail Closed，并必须说明真实 capability 与真实尝试路径。
4. 解析到 SHA 后，该 PPT 项目生命周期锁定该 SHA，不继续追踪移动中的 studio-main。
5. Harness materialization 也必须使用当前宿主真实支持的文件通道：已经存在且与 SHA 绑定并校验通过的 Runtime Bundle → GitHub Connector workflow artifact → 宿主原生文件下载的永久 GitHub Release → 宿主原生 exact-SHA archive/checkout。不得使用执行容器自身的网络栈冒充这些 fallback。
6. 如果 SHA 已经解析成功、但所有受支持的文件物化路径都不存在或失败，应 Fail Closed 为 `Harness materialization capability unavailable`；不能误报为“无法解析 SHA”，也不能要求 Recovery ZIP 代替 NEW 项目 Harness。
7. Runtime artifact 名为 `ppt-master-studio-runtime`；永久 Release 使用 tag=`studio-runtime-<SHA>`、asset=`ppt-master-studio-runtime-<SHA>.zip`。该 Runtime ZIP 是可执行 Harness 快照，不是项目 Recovery Bundle。
8. 将该精确 commit 的源码物化到当前运行环境后，读取 `studio/VERSION.json`、`studio/PROJECT_BOOTSTRAP.md`、`skills/ppt-master/SKILL.md`；运行官方 attribution_guard；再读取 Studio Authority/Workflow/Template/Regression，serverless/ChatGPT 还必须读取 Static UI/Recovery/Host Capability Rules。
9. 运行：`python3 studio/scripts/enforced_bootstrap.py --repo-root <repo-root> --running-commit <PINNED_SHA>`。失败即停止，不得绕过。
10. 读取官方 `skills/ppt-master/workflows/routing.md`，选择且只选择一个顶层工作流；官方 workflow 是执行核心，Studio 只叠加宿主适配与质量策略。
11. 创建初始 `project_state.json` checkpoint，并写入 repository=`dycm8009/ppt-master-studio`、ref=`studio-main`、commit=`<PINNED_SHA>`。

【RESUME：已有 PPT / 新聊天 / 环境重置】
12. 优先读取 project_state.json。若存在 harness.commit，必须加载该精确 commit，而不是当前 studio-main 最新 HEAD。
13. RESUME 同样先执行 Host Capability Detection；当前会话无法读取 GitHub 时，不得通过执行容器联网猜测、替换或静默升级 pinned Harness commit。
14. 若 project_state.json 或工程目录因运行环境重置而丢失，先寻找/要求最近一次 `*.ppt-recovery.zip`，校验 manifest 与 SHA-256 后恢复，再运行 `enforced_preflight.py <project> --running-commit <PINNED_SHA>`。
15. Recovery Bundle 只对 RESUME/恢复路径有权威性；没有有效 Recovery Bundle 且续作所需真实工件已经丢失时必须 Fail Closed。不得根据聊天记忆伪造 project_state、spec_lock、accepted receipts、SVG 或 QA 结果。
16. 如果用户提供的是普通 handoff/source ZIP，而不是含 `PPT_MASTER_RECOVERY_MANIFEST.json` 且 schema 为 `ppt-master-portable-recovery/*` 的 Recovery Bundle，必须把它当作输入材料，而不是恢复凭证。
17. 只有用户明确要求升级一个正在进行的项目时，才允许做 Harness migration；不得静默把旧项目升级到 studio-main 最新版本。

【ChatGPT 交互适配】
18. Default Generate 的用户决策闭环顺序保持：Stage 1（Communication + Template）→ Stage 2（Final Deck Plan）→ Deck Review；Custom Motion 被激活时增加 Motion Review。`studio/scripts/static_ui_adapter.py validate` 始终是唯一可生成 accepted receipt 的 authority；不能凭聊天文字、截图、artifact 本地状态或“已确认”假定 Gate 已通过。
19. 在 ChatGPT 宿主中，如果当前 host 已验证支持 chat-inline interactive UI artifact 的嵌入渲染与本地 reactive interaction，优先使用 `python -m studio.artifact_ui_poc.build_artifact <surface> <project>` 生成对应 Stage 1 / Stage 2 / Deck Review / Motion Review 的 inline artifact package。Artifact 只是呈现/编辑宿主，必须遵守 `studio/artifact_ui_poc/PARITY_CONTRACT.md`，不得维护第二套 canonical IDs、enum、hash、模板候选、动画 registry 或 response contract。
20. 当前已验证的聊天内 artifact host 没有受支持的 artifact → assistant callback。Artifact Confirm 只能产生 local `captured`；必须通过界面的“复制并继续”复制完整 canonical JSON，用户粘贴并发送后，再调用 `static_ui_adapter.py validate`。`captured` 不等于 `delivered`，更不等于 `accepted`。如果未来 host-native callback 被正式支持，只替换 transport 层，不改变 canonical payload 与 validator authority。
21. 如果 artifact package 无法构建、当前宿主无法可靠渲染 artifact、或 surface 不满足 artifact 的 fail-closed 自包含要求，则回退到 Studio Static UI Adapter 的版本化 HTML。回退不是降低 authority：HTML 仍只做本地交互并输出 canonical JSON，用户回传后仍必须由 `static_ui_adapter.py validate` 生成 accepted receipt。
22. Stage 1/2 固定 UI 与 artifact UI 都随用户语言本地化；canonical IDs/enum 保持官方值。Stage 2 三套方向必须提供整页视觉样本；Visual Style、Mode、Icons、Image Strategy 必须提供各自适合的视觉/语义反馈，不能退化为仅文字+色板。Deck Review artifact 可提供实时 SVG 编辑、undo/redo/reset，但最终必须表达成官方 `changes[]` 与 validator-compatible `svg_roster_sha256`。Motion Review 只在官方 motion plan 存在时启用，并使用官方 transition/object-animation registry。
23. Static UI fallback HTML 必须使用 Adapter 返回的唯一版本化文件名（UTC 时间戳 + 内容 digest），不得复用或重新提供 `confirm_stage1.html`、`confirm_stage2.html`、`deck_review.html`、`motion_review.html` 这类固定名。每次 rebuild 后以 `static_ui/latest.json` 为当前页面指针，并把本次 build 返回的新路径发给用户；不要让用户继续打开聊天历史中的旧 HTML。

【长 Deck / 图片 / 动画 / QA】
24. 18 页及以上执行 Studio Deck-level Art Direction：Deck Rhythm、Composition Diversity、Primary Visual Carrier、Section Personality、Similarity Gate；默认同一构图连续不超过 2 页，禁止“标题+卡片”万能回退。
25. 图片依次经过 Image Opportunity → Semantic Necessity → Template Compatibility → Image Role Fitness → Treatment & Placement；图片不是多样性配额，0 张图片合法。General + Dark Tech 默认 SVG-native，禁止 ambient/full-bleed raster/AI 背景和 dense HUD 概念图，除非真实证据型图片确有必要并放在明确内容容器中。
26. 长 Deck 禁止 deck-wide auto animation；默认 transition none，章节边界可克制 fade；对象动画只服务讲解顺序并受 Motion Budget。Breathing/Anchor 页面默认静态。
27. 最终导出前完成官方 SVG Quality Gate，并按 Studio 策略完成 Render Review、Deck Diversity/Similarity Audit、图片兼容性审计（如有）、Motion Audit（如有）、PPTX Postflight。Beautify/Convert 默认保持原始内容、事实与页序，除非用户明确授权改写。

【GitHub 分支纪律】
28. main 保持 upstream 镜像；studio-main 只放通过回归的稳定 Studio Overlay；studio-dev 用于修改和测试。普通 PPT 永远不使用 studio-dev，除非用户明确要求测试开发版。
29. Studio 修改先进入受控开发/修复分支并通过 GitHub Actions regression，再用 PR 晋升到 studio-main。手工上传 ZIP 不再是源码 authority；Runtime Artifact/Release 由 GitHub 自动生成并与稳定 commit SHA 绑定。
